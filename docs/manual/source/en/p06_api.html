Why there are two databases

So that nothing done while programming (manual tests, migrations with dotnet ef) can ever touch the real data. AppDbContextFactory, used by the dotnet ef tools, also always points to eggs.dev.db.

UseEggsApp(): the order in which a request is handled

  1. UseDefaultFiles() + UseStaticFiles(): if the request is for a file that exists in wwwroot (JS, CSS, icon), it is returned. index.html is sent with Cache-Control: no-cache, so after an update the old interface is never shown.
  2. The /api group with each area's endpoints: MapHealth, MapCustomers, MapSales, MapPayments, MapExpenses, MapReports, MapBackups.
  3. Any other route under /api/… → 404.
  4. Any other route (for example /clientes/abc) → index.html. That way React decides which screen to show, and reloading the page on any screen works.

Vertical Slice Architecture: how the code is organized

Many applications split code by kind (all controllers together, all services together…). Here it is split by feature: each folder in Features/ holds everything for one area, and inside it there is one file per action. One complete action, from the route to the database, is a "vertical slice".

Features/Sales/
  Sale.cs               The Sale and SaleItem entities, and how they are stored (EF configuration).
  SaleContracts.cs      What comes in (SaleCommand) and what goes out (SaleDetail, SaleListResponse).
  SaleValidator.cs      Checks the command and turns it into SaleFields, or returns Spanish errors.
  SaleEndpoints.cs      The /api/sales routes and which action each one calls.
  CreateSale.cs         Action: create.       UpdateSale.cs  Action: edit.
  DeleteSale.cs         Action: delete.       GetSale.cs     Action: read one.
  ListSales.cs          Action: list.         FindLastPrices.cs  Action: last prices.
  SaleLines.cs          Helper: writes the lines and calculates the total.
  SaleCredit.cs         Rules for credit sales and the payment made with the sale.
  SaleStatuses.cs       Works out what each credit sale still owes (Chapter 8).

The areas are: Sales, Payments (abonos), Customers, Expenses (expenses and expense types), Reports (summaries), Backups, Health and Common (shared pieces).

The order in which a new action is built

Command → Validator → Handler → Entity → Endpoint → Migration. That is: first what data comes in, then how it is checked, then what it does, then how it is stored, then the route, and finally the database change.

A request's journey, piece by piece

1. Command: what the interface sends

A C# record with every field as text or nullable, so that reading the JSON never fails: any problem is reported by the validator with a Spanish message.

public sealed record SaleCommand(
    string? Date,                          // "2026-11-23"
    IReadOnlyList<SaleItemCommand?>? Items,
    bool IsCredit = false,
    Guid? CustomerId = null,
    long? PaidNow = null,
    NewCustomerCommand? NewCustomer = null);

2. Validator: checks and translates

SaleValidator.Validate(command) returns two things: a dictionary of errors by field (for example "items[1].unitPrice" → "Escriba el precio por cartón.", "Enter the price per carton.") and, only when there are no errors, a SaleFields that already has safe types (DateOnly, CartonType, long). The field names in the errors are the same ones the interface uses, so it shows each message next to its input.

3. Handler: the action

A static class with a HandleAsync(AppDbContext db, …) method. It is the only thing that reads and writes the database. For example, the whole of CreateSale:

public static async Task<Outcome<SaleDetail>> HandleAsync(AppDbContext db, SaleFields fields)
{
    // Does the chosen customer still exist?
    if (await SaleCredit.CheckNewCustomerAsync(db, fields.CustomerId) is { } problem)
        return Outcome<SaleDetail>.Invalid(SaleCredit.CustomerField, problem);

    var sale = new Sale {
        SaleDate = fields.Date,
        IsCredit = fields.IsCredit,
        CustomerId = SaleCredit.ResolveCustomer(db, fields),  // creates the new customer if one is sent
    };
    db.Sales.Add(sale);
    SaleLines.Add(db, sale, fields.Items);                    // lines + total (the server calculates it)
    SaleCredit.ApplyPaidNow(db, sale, current: null, fields.PaidNow); // "¿Pagó algo ahora?" payment
    await db.SaveChangesAsync();                             // ONE transaction: all or nothing

    return Outcome<SaleDetail>.Done(await SaleCredit.DescribeAsync(db, sale));
}
All or nothing

The sale, its lines, the payment made on the spot and a new customer are added to the context and written by a single SaveChangesAsync(). EF Core does it in one transaction: if anything fails, nothing is half-saved.

4. Outcome: the result of an action that writes

Features/Common/Outcome.cs defines a result with four possibilities and turns it into the HTTP response:

OutcomeHTTP responseWhen
Done(value)200, 201 or 204It worked. The endpoint picks which.
Invalid(field, message)400 with errorsA field is wrong, but it can only be known by looking at the database (e.g. "Ese cliente ya no existe" — that customer no longer exists).
Refused(message)409 with { "message": … }The whole action goes against a business rule (e.g. deleting a customer who owes money).
NotFound()404Nothing active with that id.

The 409 message (Refusal) is written to be shown to the person as-is. The interface reads it from ApiError.refusal.

5. Endpoint: the route

sales.MapPost("/", async (AppDbContext db, SaleCommand command) =>
{
    var (errors, fields) = SaleValidator.Validate(command);
    if (fields is null) return Results.ValidationProblem(errors);   // 400

    var outcome = await CreateSale.HandleAsync(db, fields);
    return outcome.ToResult(sale => Results.Created($"/api/sales/{sale.Id}", sale)); // 201
}).WithName("CreateSale");

ASP.NET Core supplies the AppDbContext automatically (dependency injection) and turns the JSON body into a SaleCommand.
