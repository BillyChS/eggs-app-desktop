Chapter 7The data layer

AppDbContext: the door to the database

Data/AppDbContext.cs is the EF Core class that represents the database. It has one property per table:

Customers · Sales · SaleItems · Payments · ExpenseCategories · Expenses

AppDbContext.Configure(options, filePath) is the only place that defines how the app connects: SQLite, with foreign keys turned on, and two interceptors (below). When building the model (OnModelCreating) it does three things for every entity:

  1. Applies each entity's configuration (the …Configuration classes that sit next to each entity).
  2. Rejects any decimal property with an error. Money is stored as long (whole colones) because SQLite can't sum decimal. The error fires even when creating a migration, before the problem reaches a table.
  3. For every entity that inherits BaseEntity: the Id is never generated by the database (the code generates it), and it gets the global filter "SoftDelete", which hides rows with IsDeleted = true from every query.

BaseEntity and soft delete

public abstract class BaseEntity
{
    public Guid Id { get; private init; } = Guid.NewGuid();   // generated in code
    public DateTime CreatedAt { get; internal set; }
    public DateTime UpdatedAt { get; internal set; }
    public bool IsDeleted { get; internal set; }
}

AuditInterceptor hooks into every SaveChanges and, before writing:

  • New rows: sets CreatedAt and UpdatedAt to local time (DateTime.Now).
  • Modified rows: updates UpdatedAt and protects CreatedAt.
  • Deleted rows: turns them into "modified" with IsDeleted = true. That's why db.Sales.Remove(sale) never really deletes.
Soft delete pitfalls
  • EF Core's ExecuteUpdate and ExecuteDelete skip the interceptor: they set no timestamps and really delete. They are not used on entities.
  • Soft delete does not cascade to related rows that aren't loaded. That's why DeleteSale loads the lines (Include(Items)) and deletes them along with the sale.
  • A unique index still counts deleted rows unless it has a filter. The unique index on expense type names has HasFilter("\"IsDeleted\" = 0").
  • To also read deleted rows, use IgnoreQueryFilters([AppDbContext.SoftDeleteFilter]), for example to show a deleted customer's name on an old sale.

SqlitePragmaInterceptor runs PRAGMA synchronous = FULL; on every connection: each save waits for the disk to confirm it, so a power cut can't lose a sale that was already saved. In addition, the migrator puts the database in WAL (write-ahead log) mode once per startup; that's why, while the app runs, eggs.db-wal and eggs.db-shm exist next to eggs.db.

The data model

Notes per table

TableWhat to know
CustomersNo unique index on the name: two people can have the same name. The interface asks before saving a similar name. A deleted customer stays in the table (their sales name them).
SalesSaleDate is a DateOnly: it has no time, so no time zone can move it to another day. Indexed by date. It has no navigation property to the customer on purpose: if the customer is deleted, EF would quietly return it empty. The name is read with CustomerAccounts.FindRefsAsync.
SaleItemsThe price is stored on each line because it changes from sale to sale. LineTotal = quantity × price, calculated by the server. Limits: 20 lines per sale, quantity up to 10,000, price up to ₡1,000,000. CartonType is stored as a one-letter string.
PaymentsA payment always belongs to a customer, which never changes. SaleId and ForSaleId are optional and usually empty (see Chapter 8). Indexed by date.
ExpenseCategoriesExpense types are rows, not code. The migration seeds 8 with fixed ids: Alimento (feed), Vitaminas, Desparasitantes (dewormers), Burucha (wood shavings), Cartones, Plásticos/Envoltorios (wrapping), Equipo (equipment) and Otro (other) (…0001 to …0008). "Otro" has NeedsDescription = true.
ExpensesAn expense counts on its ExpenseDate. Its type is never deleted, only "retired".

Data rules that are not negotiable

RuleWhy
Money as long, whole colonesSQLite doesn't sum decimal; the business doesn't use cents.
Guid keys generated in codeThe object has its id before it is saved, which lets the sale, lines, payment and a new customer be linked and written in a single save.
Business dates as DateOnly; times with DateTime.NowAlways Costa Rica local time, never UtcNow: at 6 p.m. in Costa Rica it's already the next day in UTC.
Totals and balances are never stored "on the side"A customer's balance and what each credit sale owes are calculated on every read from the sales and payments. So they can never drift.
No .db file is ever committed to gitIt's the family's data.

How they are applied: DatabaseMigrator

Nothing has to be run by hand. Every time the app starts, before it takes any request, DatabaseMigrator.MigrateAsync:

  1. Checks whether the file already has data (exists and is larger than 0 bytes).
  2. Compares the migrations the program knows with the ones the database already has. If the database has migrations the program doesn't know (it comes from a newer version), it stops with an error: it never works on a schema it doesn't understand.
  3. If there are pending migrations and there is data, it first makes a copy in backups\eggs-YYYY-MM-DD_HH-mm-ss-fff.db (the 5 newest are kept).
  4. Puts the database in WAL mode.
  5. Drops a possibly abandoned migration lock (__EFMigrationsLock) and applies the migrations.

Any failure becomes a DatabaseMigrationException; the app shows "No se pudo abrir Eggs App. No se borró ningún dato." ("Eggs App couldn't open. No data was deleted.") and doesn't start.

How to create a new migration

dotnet tool restore            # once per clone: installs dotnet-ef
