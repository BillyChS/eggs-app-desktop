AppDbContext: la puerta a la base de datos

Data/AppDbContext.cs es la clase de EF Core que representa la base de datos. Tiene una propiedad por tabla:

Customers · Sales · SaleItems · Payments · ExpenseCategories · Expenses

AppDbContext.Configure(options, rutaDelArchivo) es el único lugar que define cómo se conecta la app: SQLite, con llaves foráneas activadas, y dos interceptores (abajo). Al crear el modelo (OnModelCreating) hace tres cosas para todas las entidades:

  1. Aplica la configuración de cada entidad (las clases …Configuration que están junto a cada entidad).
  2. Rechaza cualquier propiedad decimal con un error. El dinero se guarda como long (colones enteros) porque SQLite no sabe sumar decimal. El error salta incluso al crear una migración, antes de que el problema llegue a una tabla.
  3. A toda entidad que herede de BaseEntity: el Id nunca lo genera la base de datos (lo genera el código) y se le pone el filtro global "SoftDelete", que esconde las filas con IsDeleted = true de todas las consultas.

BaseEntity y el borrado lógico

public abstract class BaseEntity
{
    public Guid Id { get; private init; } = Guid.NewGuid();   // se genera en el código
    public DateTime CreatedAt { get; internal set; }
    public DateTime UpdatedAt { get; internal set; }
    public bool IsDeleted { get; internal set; }
}

AuditInterceptor se mete en cada SaveChanges y, antes de escribir:

  • Filas nuevas: pone CreatedAt y UpdatedAt con la hora local (DateTime.Now).
  • Filas modificadas: actualiza UpdatedAt y protege CreatedAt.
  • Filas borradas: las cambia a "modificadas" con IsDeleted = true. Por eso db.Sales.Remove(venta) nunca borra de verdad.
Trampas del borrado lógico
  • ExecuteUpdate y ExecuteDelete de EF Core se saltan el interceptor: no ponen fechas y sí borran de verdad. No se usan con entidades.
  • El borrado lógico no se propaga a filas relacionadas que no estén cargadas. Por eso DeleteSale carga las líneas (Include(Items)) y las borra junto con la venta.
  • Un índice único sigue contando las filas borradas, salvo que tenga un filtro. El índice único de nombres de tipos de gasto tiene HasFilter("\"IsDeleted\" = 0").
  • Para leer también lo borrado se usa IgnoreQueryFilters([AppDbContext.SoftDeleteFilter]), por ejemplo para mostrar el nombre de un cliente borrado en una venta vieja.

SqlitePragmaInterceptor ejecuta PRAGMA synchronous = FULL; en cada conexión: cada vez que se guarda algo, SQLite espera a que el disco lo confirme, así un apagón no puede perder una venta ya guardada. Además, el migrador pone la base en modo WAL (write-ahead log) una vez por arranque; por eso, mientras la app corre, junto a eggs.db existen eggs.db-wal y eggs.db-shm.

Notas por tabla

TablaLo que hay que saber
CustomersNo hay índice único por nombre: dos personas pueden llamarse igual. La interfaz pregunta antes de guardar un nombre parecido. Un cliente borrado sigue en la tabla (sus ventas lo nombran).
SalesSaleDate es DateOnly: no tiene hora, así que ninguna zona horaria la puede mover de día. Índice por fecha. No tiene propiedad de navegación al cliente a propósito: si el cliente está borrado, EF la devolvería vacía sin avisar. El nombre se lee con CustomerAccounts.FindRefsAsync.
SaleItemsEl precio se guarda en cada línea porque cambia de venta a venta. LineTotal = cantidad × precio, calculado por el servidor. Límites: 20 líneas por venta, cantidad hasta 10.000, precio hasta ₡1.000.000. CartonType se guarda como texto de una letra.
PaymentsUn abono siempre es de un cliente, que nunca cambia. SaleId y ForSaleId son opcionales y casi siempre vacíos (ver Capítulo 8). Índice por fecha.
ExpenseCategoriesLos tipos de gasto son filas, no código. La migración siembra 8 con ids fijos: Alimento, Vitaminas, Desparasitantes, Burucha, Cartones, Plásticos/Envoltorios, Equipo y Otro (…0001 a …0008). "Otro" tiene NeedsDescription = true.
ExpensesUn gasto cuenta en su ExpenseDate. Su tipo nunca se borra, solo se "retira".

Reglas de datos que no se negocian

ReglaPor qué
Dinero en long, colones enterosSQLite no suma decimal; el negocio no usa céntimos.
Llaves Guid generadas en el códigoEl objeto tiene id antes de guardarse, lo que permite enlazar venta, líneas, abono y cliente nuevo en un solo guardado.
Fechas de negocio en DateOnly; horas en DateTime.NowSiempre la hora local de Costa Rica, nunca UtcNow: a las 6 p. m. en Costa Rica, en UTC ya es el día siguiente.
Totales y saldos nunca se guardan "aparte"El saldo de un cliente y lo que debe cada fiado se calculan en cada lectura desde las ventas y abonos. Así nunca se pueden descuadrar.
Nunca se guarda un archivo .db en gitSon datos de la familia.

Cómo se aplican: DatabaseMigrator

No hay que correr nada a mano. Cada vez que la app arranca, antes de aceptar pedidos, DatabaseMigrator.MigrateAsync:

  1. Mira si el archivo ya tiene datos (existe y pesa más de 0).
  2. Compara las migraciones que conoce el programa con las que ya tiene la base. Si la base tiene migraciones que el programa no conoce (es de una versión más nueva), se detiene con error: nunca trabaja sobre una estructura que no entiende.
  3. Si hay migraciones pendientes y hay datos, primero hace una copia en backups\eggs-AAAA-MM-DD_HH-mm-ss-fff.db (se guardan las 5 más nuevas).
  4. Pone la base en modo WAL.
  5. Borra un posible candado de migración abandonado (__EFMigrationsLock) y aplica las migraciones.

Cualquier falla se convierte en DatabaseMigrationException, la app muestra "No se pudo abrir Eggs App. No se borró ningún dato." y no arranca.

Cómo se crea una migración nueva

dotnet tool restore            # una vez por copia del repositorio: instala dotnet-ef
dotnet ef migrations add NombreDelCambio --project src/EggsApp.Api --output-dir Data/Migrations
