Por qué hay dos bases de datos

Para que nada de lo que se haga mientras se programa (pruebas a mano, migraciones con dotnet ef) pueda tocar los datos reales. AppDbContextFactory, que usan las herramientas dotnet ef, también apunta siempre a eggs.dev.db.

AddEggsApp(): los servicios

builder.Services.AddDbContext<AppDbContext>(...)  // la base de datos, con la ruta de Database:Path
builder.Services.TryAddSingleton(FailureLog.Default) // el registro de fallas
builder.Services.TryAddSingleton(new BackupClock())  // la hora (reemplazable en pruebas)
builder.Services.AddSingleton<DatabaseBackups>()     // los respaldos
builder.Services.AddHostedService<BackupWorker>()    // la tarea que respalda cada hora

UseEggsApp(): el orden en que se atiende un pedido

  1. UseDefaultFiles() + UseStaticFiles(): si piden un archivo que existe en wwwroot (JS, CSS, ícono), se devuelve. index.html se marca Cache-Control: no-cache, para que tras una actualización nunca se muestre la interfaz vieja.
  2. El grupo /api con los endpoints de cada área: MapHealth, MapCustomers, MapSales, MapPayments, MapExpenses, MapReports, MapBackups.
  3. Cualquier otra ruta bajo /api/… → 404.
  4. Cualquier otra ruta (por ejemplo /clientes/abc) → index.html. Así React decide qué pantalla mostrar, y recargar la página en cualquier pantalla funciona.

Vertical Slice Architecture: cómo está organizado el código

En muchas aplicaciones el código se separa por tipo (todos los controladores juntos, todos los servicios juntos…). Aquí se separa por funcionalidad: cada carpeta de Features/ tiene todo lo de un área, y dentro hay un archivo por acción. Una acción completa, de la ruta a la base de datos, es una "rebanada vertical" (vertical slice).

Features/Sales/
  Sale.cs               Las entidades Sale y SaleItem, y cómo se guardan (configuración EF).
  SaleContracts.cs      Lo que entra (SaleCommand) y lo que sale (SaleDetail, SaleListResponse).
  SaleValidator.cs      Revisa el comando y lo convierte en SaleFields, o da errores en español.
  SaleEndpoints.cs      Las rutas /api/sales y qué acción llama cada una.
  CreateSale.cs         Acción: crear.        UpdateSale.cs  Acción: editar.
  DeleteSale.cs         Acción: borrar.       GetSale.cs     Acción: leer una.
  ListSales.cs          Acción: listar.       FindLastPrices.cs  Acción: últimos precios.
  SaleLines.cs          Ayuda: escribe las líneas y calcula el total.
  SaleCredit.cs         Reglas de fiados y del abono que se paga con la venta.
  SaleStatuses.cs       Cálculo de cuánto debe cada fiado (Capítulo 8).

Las áreas son: Sales (ventas), Payments (abonos), Customers (clientes), Expenses (gastos y tipos de gasto), Reports (resúmenes), Backups (respaldos), Health (estado) y Common (piezas compartidas).

El orden en que se construye una acción nueva

Command → Validator → Handler → Entity → Endpoint → Migration. Es decir: primero qué datos entran, después cómo se revisan, después qué hace, después cómo se guarda, después la ruta, y por último el cambio a la base de datos.

El recorrido de un pedido, pieza por pieza

1. Command: lo que manda la interfaz

Un record de C# con todos los campos como texto o nulables, para que nada falle al leer el JSON: cualquier problema lo reporta el validador con un mensaje en español.

public sealed record SaleCommand(
    string? Date,                          // "2026-11-23"
    IReadOnlyList<SaleItemCommand?>? Items,
    bool IsCredit = false,
    Guid? CustomerId = null,
    long? PaidNow = null,
    NewCustomerCommand? NewCustomer = null);

2. Validator: revisa y traduce

SaleValidator.Validate(command) devuelve dos cosas: un diccionario de errores por campo (por ejemplo "items[1].unitPrice" → "Escriba el precio por cartón.") y, solo si no hay errores, un SaleFields, que ya tiene tipos seguros (DateOnly, CartonType, long). Los nombres de los campos en los errores son los mismos que usa la interfaz, que pone cada mensaje al lado de su casilla.

3. Handler: la acción

Una clase estática con un método HandleAsync(AppDbContext db, …). Es lo único que lee y escribe la base de datos. Por ejemplo, CreateSale completo:

public static async Task<Outcome<SaleDetail>> HandleAsync(AppDbContext db, SaleFields fields)
{
    // ¿El cliente elegido todavía existe?
    if (await SaleCredit.CheckNewCustomerAsync(db, fields.CustomerId) is { } problem)
        return Outcome<SaleDetail>.Invalid(SaleCredit.CustomerField, problem);

    var sale = new Sale {
        SaleDate = fields.Date,
        IsCredit = fields.IsCredit,
        CustomerId = SaleCredit.ResolveCustomer(db, fields),  // crea el cliente nuevo si viene
    };
    db.Sales.Add(sale);
    SaleLines.Add(db, sale, fields.Items);                    // líneas + total (lo calcula el servidor)
    SaleCredit.ApplyPaidNow(db, sale, current: null, fields.PaidNow); // abono "¿Pagó algo ahora?"
    await db.SaveChangesAsync();                             // UNA transacción: todo o nada

    return Outcome<SaleDetail>.Done(await SaleCredit.DescribeAsync(db, sale));
}
Todo o nada

La venta, sus líneas, el abono pagado en el momento y un cliente nuevo se agregan al contexto y se escriben con un solo SaveChangesAsync(). EF Core lo hace en una transacción: si algo falla, no se guarda nada a medias.

4. Outcome: el resultado de una acción que escribe

Features/Common/Outcome.cs define un resultado con cuatro posibilidades, y lo convierte a la respuesta HTTP:

OutcomeRespuesta HTTPCuándo
Done(valor)200, 201 o 204Salió bien. El endpoint decide cuál.
Invalid(campo, mensaje)400 con errorsUn campo está mal, pero solo se sabe mirando la base de datos (ej. "Ese cliente ya no existe").
Refused(mensaje)409 con { "message": … }La acción entera va contra una regla del negocio (ej. borrar un cliente que debe).
NotFound()404No hay nada activo con ese id.

El mensaje del 409 (Refusal) está escrito para mostrarse tal cual a la persona. La interfaz lo lee en ApiError.refusal.

5. Endpoint: la ruta

sales.MapPost("/", async (AppDbContext db, SaleCommand command) =>
{
    var (errors, fields) = SaleValidator.Validate(command);
    if (fields is null) return Results.ValidationProblem(errors);   // 400

    var outcome = await CreateSale.HandleAsync(db, fields);
    return outcome.ToResult(sale => Results.Created($"/api/sales/{sale.Id}", sale)); // 201
}).WithName("CreateSale");

ASP.NET Core entrega automáticamente el AppDbContext (inyección de dependencias) y convierte el JSON del cuerpo en SaleCommand.
