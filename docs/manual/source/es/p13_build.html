Comandos del día a día

dotnet build                                 # compila todo; debe dar CERO advertencias
dotnet test                                  # pruebas del servidor
dotnet run --project src/EggsApp.Api         # API sola: http://localhost:5080/swagger
dotnet run --project src/EggsApp.Desktop     # la app de escritorio (antes: pnpm build)

cd src/web
pnpm install                                 # una vez, o cuando cambia package.json
pnpm dev                                     # interfaz con recarga en caliente (y /dev/componentes)
pnpm build                                   # compila la interfaz a src/EggsApp.Api/wwwroot
pnpm lint                                    # revisa el estilo
pnpm test                                    # pruebas de la interfaz
La forma más cómoda de trabajar en la interfaz

Correr la API sola (dotnet run --project src/EggsApp.Api) y en otra terminal pnpm dev, y abrir la dirección que da Vite. Los cambios se ven al guardar, sin compilar. Se trabaja sobre eggs.dev.db, nunca sobre los datos reales.

Notas: dotnet build y dotnet test nunca corren pnpm ni necesitan la interfaz compilada. La API solo detecta wwwroot si existe al arrancar, así que después del primer pnpm build hay que reiniciarla.

Las pruebas automáticas

Interfaz (Vitest)

Los archivos *.test.ts(x) están junto al código que prueban. test/api.tsx reemplaza fetch con una API falsa (fakeApi()): cada prueba dice qué responde cada ruta y después revisa qué pedidos se hicieron. Las pantallas se dibujan con el enrutador real en memoria. test/setup.ts hace fallar la prueba si alguna pantalla se cae durante ella. La zona horaria se fija en America/Costa_Rica para que los errores de fechas aparezcan también en máquinas en UTC.

Integración continua (GitHub Actions)

  • Cada pull request detecta qué partes cambiaron y corre Backend CI (Windows: restore, build con -warnaserror, test) y/o Frontend CI (Ubuntu: pnpm install, lint, build). El trabajo ci-gate resume el resultado y es el único requerido en main.
  • Los pushes a main corren ambos. CodeQL revisa seguridad. Dependabot propone actualizaciones semanales.
  • installer.yml construye el instalador cuando se publica una etiqueta v* y crea un GitHub Release con el instalador y su SHA-256. Falla si la etiqueta no coincide con <Version>.

La versión

Se pone solo en <Version> de Directory.Build.props. Aparece abajo a la izquierda de la barra lateral ("Versión 1.3.0"), en la línea de arranque del registro, en GET /api/health, en el nombre del instalador y en la lista de programas de Windows. Se sube en el mismo pull request que cambia lo que se entrega: el último número para arreglos, el del medio para funciones nuevas, el primero para cambios en cómo se usa la app.

Publicar y crear el instalador

dotnet publish src/EggsApp.Desktop -p:PublishProfile=win-x64       # → src/EggsApp.Desktop/bin/publish/win-x64
powershell -ExecutionPolicy Bypass -File installer\build.ps1      # → artifacts\installer\EggsApp-Setup-1.3.0.exe

Qué hace la publicación:

  • Es self-contained: incluye .NET, así la PC solo necesita el runtime de WebView2 (que trae Windows 11).
  • Frontend.targets corre pnpm install --frozen-lockfile y pnpm build y copia wwwroot a la salida. Con -p:SkipFrontendBuild=true se usa el wwwroot que ya existe.
  • Se quitan archivos que la app nunca usa: EggsApp.Api.exe y su runtimeconfig (la API solo corre adentro), appsettings.Development.json y los .xml de documentación. Los .pdb se quedan para que los errores en el registro tengan número de línea.

build.ps1 además revisa que estén los archivos indispensables (EggsApp.Desktop.exe, EggsApp.Api.dll, appsettings.json, e_sqlite3.dll, wwwroot\index.html), que no se haya colado ninguno de los quitados ni ningún .db, y al final imprime el tamaño (unos 55 MB) y el SHA-256.

Instalar y actualizar en la PC

Antes de la primera instalación

  1. Smart App Control (Seguridad de Windows → Control de aplicaciones y del explorador) tiene que estar Desactivado: si está Activado o en Evaluación, bloquea apps sin firma, como esta, sin opción de abrirlas.
  2. OneDrive: iniciar sesión con la cuenta de los respaldos y dejarlo arrancando con Windows.
  3. Si se copió alguna versión a mano antes, borrar esa carpeta y sus accesos directos. Nunca borrar %LocalAppData%\EggsApp: son los datos.

Instalar o actualizar

  1. Copiar EggsApp-Setup-<versión>.exe (USB o desde el GitHub Release). Opcional: comparar Get-FileHash con el SHA-256.
  2. Ejecutarlo. SmartScreen dirá "Windows protegió su PC": Más información → Ejecutar de todas formas.
  3. Si es una actualización y la app está abierta, el instalador pide cerrarla y espera.
  4. Instalar → Finalizar con "Abrir Eggs App" marcado. Los datos, respaldos y settings.json quedan igual. Si la versión cambia la base, la app la copia a backups\ antes de migrar.

Qué revisar después

  • Abajo a la izquierda dice Versión X.Y.Z.
  • Están las últimas ventas, abonos y gastos.
  • La barra lateral dice "Último respaldo: hoy …" sin advertencia.
  • El registro del día tiene Started. Version X.Y.Z+… (y, si cambió la base, Applied migrations: …).

Desinstalar o volver a una versión anterior

Configuración → Aplicaciones → Eggs App → Desinstalar quita solo el programa; los datos se quedan y reaparecen al reinstalar. Para volver atrás: desinstalar e instalar la versión vieja. Si la nueva había cambiado la base, la vieja se niega a abrirla ("No se pudo abrir Eggs App. No se borró ningún dato."); entonces se reinstala la nueva, o se restaura la copia previa a la migración (perdiendo lo anotado después).
